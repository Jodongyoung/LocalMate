# LocalMate — 제품 기획서 (PRD) v1.1

- **개정:** 2026-10-22
- **변경 요약:** NAVER Cloud 담당자 설명 반영. 실제 점주 인터뷰 대신 가상 페르소나/공개 자료 사용, HyperCLOVA X는 *무료 접근 확인 시 우선* (비용 발생하면 학교 제공 모델), 지역 맥락과 측정 가능한 KPI를 강조. 기존 MVP B안과 고객·운영·마케팅·업무 영역을 유지.
- **문서 상태:** 제품 요구사항 확정, 구현 구체안은 `docs/00_DECISIONS.md`의 DRAFT 확인.

## 이번 개정에서 추가된 제품 원칙
1. **목표 업무:** 점주가 리뷰에서 문제를 발견해 후속 조치를 등록하는 과정의 반복 부담을 줄인다. 도메인 문제는 인터뷰 검증이 아닌 **가설**로 취급.
2. **주인공은 AI 챗창이 아니라 업무 변화:** 대표 장면은 근거 기반 인사이트 → 제안 → 명시적 승인 → 업무 생성/이력 확인.
3. **지역성(Hyper-Local):** 사업장 등록에 지역·상권 맥락을 포함하되, 출처 없는 실시간 동네 트렌드·행사·상권 통계는 만들지 않는다. 공인 로컬 데이터 연결은 권한·비용 확인 시만 도입.
4. **효과성:** 성공 지표는 처리 플로우 완주율·승인 전 무단 변경 0·중복 생성 0·DB 집계 일치. 절감 시간은 실제 측정 결과만 제시.
5. **인간 중심 승인:** 초안 미리보기는 무료/비변경 처리, 저장·작업 생성·AI 주도 상태 변경은 승인 필요. 외부 리뷰 게시·예약 변경 불가.
6. **기술 분리:** Qwen(개발 에이전트)과 서비스 내부 LLM은 별개. HCX 가능 시 우선 검증하되 비용/권한이 없으면 모델 교체 가능한 코어로 구축한다.
7. **현실성:** 과한 기능 추가보다 카페의 1개 완결 시나리오, 미용실의 업종별 차이를 먼저 검증한다.

# 제품 범위와 상세 기능

- 개정 기준일: 2026-10-22
- 목표 발표일: 2026-11-25
- 상태: **발표용 MVP의 제품 기획 확정**. 구현·외부 연동·모델 품질은 검증 전.
- 서비스 유형: PC 우선 반응형 웹서비스(모바일 브라우저 기본 대응). 네이티브 앱 개발은 제외.
- 개발 제약: 개발자 2명, Qwen 중심 구현·일상 검증, Codex 중심 설계·위험도 높은 변경 검토, 자동 테스트, 합성 데이터 허용.
- 기술 기본안: React + TypeScript + FastAPI. 실제 DB·LLM 어댑터 등 구체적 구현 선택은 기술 설계서에서 검증.

## 1. 제품 정의와 성공 기준

**한 줄 정의:** 여러 업종의 소상공인이 자신의 고객 반응과 운영 데이터를 한곳에서 살펴보고, 단일 AI 업무 비서로부터 근거 있는 개선안을 제안받아, 승인 후 **내부 업무만 실제 실행·기록**할 수 있는 서비스.

**핵심 차별점:** `매장 데이터 → 근거 기반 진단 → 업무 제안 → 승인 → 서버 실행 → DB 및 화면의 결과·이력`을 하나의 서비스에서 완결한다. 일반적인 문구 생성형 챗봇처럼 답변만 출력하고 끝내지 않는다.

**MVP 성공 정의:**
1. 카페와 미용실에서 **같은 Agent 코어**가 사업장별 도구·운영 데이터를 달리 조회한다.
2. 리뷰·문의 분석, 카페의 매출 분석, 미용실의 예약 분석, 마케팅 초안 기능이 실제 API와 DB를 통해 작동한다.
3. 최소 하나의 **자발적 업무 제안**이 사용자의 별도 채팅 요청 없이 대시보드에 나타난다.
4. 사용자가 승인한 **내부 작업**(업무 생성·상태 변경·응대/마케팅 초안 저장)만 실제 반영된다.
5. 실행 결과와 실패·재시도 이력이 남고, 서로 다른 사업장 데이터는 권한으로 격리된다.
6. 합성 입력 자료를 사용해도 통계는 DB에서 계산하고, AI 분석·생성은 실제 승인된 모델 API로 수행한다. 모델 Mock을 쓰는 경우 **데모/모의 모드**라고 명확히 표시한다.

## 2. 사용자와 권한 모델

- **Owner(사장님):** 자신에게 권한이 부여된 사업장을 선택하고 데이터 등록·열람, AI 요청, 제안 승인·거절, 내부 업무·초안 관리.
- **시연 계정:** 합성 사업장별 Owner 계정 최소 2개(또는 한 계정의 두 승인된 사업장). 사업장 권한 격리 테스트에는 서로 권한이 겹치지 않는 계정 2개가 필수.
- **직원별 세분화 권한, 사업장 초대·가입 자동화, 결제/구독:** MVP 범위 제외. 다만 서버 모델은 `User ↔ BusinessMembership ↔ Business`의 확장 가능한 관계를 사용한다.
- **인증:** 테스트용 고정 화면 로그인만으로 사용자 권한을 대체하지 않는다. 백엔드에서 사용자 인증 및 사업장 소속 검증을 수행한다. MVP에서는 가입·비밀번호 찾기까지 완전한 회원 서비스는 구현하지 않아도 된다.

## 4. 구체적 업종별 서비스 정의

### 카페 (데모 사업장 A)
- 공통 입력: 고객 리뷰/문의, 매장 소개·운영 시간·고객 응대 원칙.
- 업종 입력: `sales` 데이터 — 판매일시(최소 날짜·시간대), 메뉴 ID/명, 판매 수량, 판매 단가 또는 매출액.
- 통계: 총매출, 판매 수량, 인기 메뉴, 시간대별 판매량, 최근 기간 변화.
- 주요 인사이트: 대기 시간·품절·응대 관련 반복 불만, 높은 주문 집중 시간대, 운영 점검 제안.
- 예시 내부 실행: `혼잡 시간 주문 동선 점검` 업무 생성, 고객 답변 초안 저장, 프로모션 초안 저장.
- **해석 제한:** 판매량이 높다는 사실만으로 대기의 인과 원인을 확정하지 않는다. 리뷰 발생 시간 정보가 없으면 시간대 간 직접 상관을 주장하지 않는다.

### 미용실 (데모 사업장 B)
- 공통 입력: 고객 리뷰/문의, 매장 소개·서비스 안내·예약 운영 원칙.
- 업종 입력: `bookings` 데이터 — 예약 시작일시, 시술 종류, 예정 소요시간, 상태(예약/완료/취소 등), 합성 직원/리소스 ID 선택.
- 통계: 날짜·시간대별 예약 수, 상태별 비율, 인기 시술, 예약 집중 시간대.
- 주요 인사이트: 예약 지연·응대 관련 반복 불만과 혼잡 시간대, 예약 간격 검토 제안.
- 예시 내부 실행: `예약 간격 점검` 업무 생성, 예약 안내 문구 초안 저장, 이벤트 초안 저장.
- **해석 제한:** 예약 건수만으로 실제 지연 원인이나 실측 대기 시간을 단정하지 않는다.

**범용성 검증:** 사업장을 전환해도 동일한 채팅·업무·승인·이력 UI를 사용하고, `BusinessType`에 따라 데이터 조회 도구와 분석 카드만 달라진다. 단순 사업장명 변경으로 범용성을 시연하지 않는다.

## 5. 화면·정보 구조

PC 기준 좌측 내비게이션 + 상단 사업장 전환. 모바일 브라우저는 내비게이션 접기와 주요 정보의 세로 배치를 지원.

| 화면 | 주요 표시 요소 | 핵심 동작 |
|---|---|---|
| 로그인/사업장 전환 | 계정 상태, 선택 가능 사업장 | 로그인, 선택, 잘못된 사업장 접근 거부 |
| 대시보드 | 오늘/최근 기간 지표, 반복 문제, AI 인사이트, 승인 대기 | 증거 보기, AI에게 질문, 제안 상세 이동 |
| AI 비서 | 대화 이력, 참조 데이터, 계획 미리보기 | 자연어 분석 요청, 도구 기반 답변, 승인 화면 이동 |
| 고객 관리 | 리뷰·문의 목록, 감정/측면 필터, 분석 상태, 답변 초안 | 등록/CSV, 분석 요청, 원문·근거 보기 |
| 매장 운영 | 업종에 따라 매출 또는 예약 통계, 파일 업로드 | 기간 선택, 업로드, 문제 탐색 |
| 마케팅 | 생성한 홍보·이벤트 초안, 근거/정책, 상태 | 새 초안 생성, 승인 요청, 수정/보관 |
| 업무 관리 | 제안/승인 대기/실행/완료/실패 목록, 이력 | 승인·거절·결과 확인, 직접 상태 관리 |
| 사업장 설정 | 업종, 사업장 소개, 운영 정책·톤, 합성 데이터 초기화 | 정보 수정, 업로드 상태 확인 |

화면 수를 줄여야 한다면 `마케팅`은 `AI 비서`의 초안 탭과 합쳐도 된다. 필수 사용자 흐름은 보존한다.

## 6. 주요 사용자 시나리오 및 수용 기준

### SCN-01: 카페 리뷰에서 실제 업무까지
1. 카페 선택 → 합성 리뷰·매출 데이터 준비.
2. 리뷰 분석이 완료되면 대기 관련 부정 피드백 건수를 **DB에서 집계**하고 각 리뷰 ID·근거 인용을 제시.
3. 데이터 갱신 후 사용자가 채팅하기 전에도 대시보드에 점검 인사이트 표시.
4. 사장님: “어떤 문제가 반복되고 있나요?” → AI가 근거가 확인되는 문제와 매출 집중 시간대(있을 때만)를 구분하여 답변.
5. AI가 `혼잡 시간 주문 동선 점검` 업무 생성과 고객 응대 초안을 **제안만** 한다.
6. 사장님이 제안별 대상·내용·효과를 확인하고 승인.
7. 서버가 승인된 `create_task`와 `save_reply_draft`를 실행해 DB 저장.
8. 업무 목록·초안 목록·실행 이력에 결과 표시. 동일 승인 재전송은 두 번 만들지 않는다.

### SCN-02: 미용실 예약 운영
1. 미용실 선택 → 합성 리뷰·예약 데이터 준비.
2. 예약 집중 시간대와 예약 지연 관련 피드백을 각각 집계.
3. AI가 `예약 간격 점검` 업무와 고객 안내 메시지 초안을 제안.
4. 승인 후 내부 업무·초안 저장, 상태·이력 확인.
5. 카페와 다른 운영 도구를 사용했음을 검증.

### SCN-03: 분석 실패 및 권한 차단
- LLM 실패/비정상 JSON: `FAILED`로 남기고 정상 중립으로 바꾸지 않는다. 재시도 또는 수동 확인 유도.
- 카페 계정으로 미용실의 원문/작업/대화 ID 직접 접근: 거부, 모델 전달도 금지.
- 승인 거절: 실행 없음, 사유/결정 이력만 남긴다.
- 승인 후 계획 변경: 이전 승인은 무효.

## 7. AI 비서 동작 및 도구 계약

### 7.1 AI의 책임과 서버의 책임
- AI: 사용자 요청 의도 이해, 필요한 데이터 조회 계획, 리뷰의 측면·의도·근거 구조화, 인사이트 설명, 고객 응대·마케팅·업무 제안의 **후보 생성**.
- 백엔드: 사업장 권한 검증, 데이터 조회, 숫자 집계, 분석 스키마 및 근거 확인, 허용 도구 선택, 승인 상태 결정, 실제 DB 변경, 실행 이력 기록.
- 모델 출력은 **권한·승인·작업 완료 여부에 대한 진실의 원천이 아님**.

### 7.2 P0 허용 도구(예시 내부 식별자)

| 구분 | 도구 | 권한·효과 |
|---|---|---|
| 읽기 | `get_business_context` | 소속 사업장 정보/정책의 허용 필드 조회 |
| 읽기 | `get_feedback_summary` | 사업장·기간·측면별 리뷰 통계 및 근거 ID |
| 읽기 | `get_sales_summary` | 카페에만 허용, 기간·메뉴·시간대 집계 |
| 읽기 | `get_booking_summary` | 미용실에만 허용, 예약 현황 집계 |
| 생성(미리보기) | `prepare_reply_draft` | 화면상의 고객 답변 초안만 생성 |
| 생성(미리보기) | `prepare_marketing_draft` | 화면상의 마케팅 초안만 생성 |
| 변경 | `create_task` | **명시적 승인 후에만** 내부 업무 저장 |
| 변경 | `save_reply_draft` | **AI 제안 실행인 경우 승인 후에만** 초안 저장 |
| 변경 | `save_marketing_draft` | **AI 제안 실행인 경우 승인 후에만** 초안 저장 |
| 변경 | `update_task_status` | AI 제안 실행인 경우 **승인 후에만** 허용된 상태 변경 |

사용자가 직접 화면에서 리뷰를 등록·수정하거나 파일을 업로드·저장 버튼을 누르는 동작은 명시적 사용자 조작이므로 별도의 AI 제안 승인 절차를 요구하지 않는다. 대화 저장, 분석 결과 캐시, 인사이트 계산 및 승인 대기 제안 저장 등 **비업무 효과 기록** 역시 자동 저장 가능하다. 단, 민감정보 최소 보관·권한 검사를 적용한다.

### 7.3 승인 상태 머신

`PROPOSED → PENDING_APPROVAL → APPROVED / REJECTED / EXPIRED`.

승인된 계획은 실행 경로에서 `APPROVED → RUNNING → SUCCEEDED / FAILED / UNKNOWN`으로 별도 추적한다.

- 서버는 사업장 ID, 사용자 권한, 도구명, 인자, 초안 본문, 계획 버전/해시를 승인 대상에 고정.
- AI는 `approved=true` 같은 문장으로 승인을 만들 수 없음.
- 실행 직전 권한·버전·대상 상태를 재검증.
- 멱등키와 DB 제약으로 중복 내부 저장 방지. 외부 효과가 도입되면 별도 강화 필요.
- 계획이 변경되면 새 승인 요청을 생성한다.
- 실제 게시·예약 변경·고객 발송 도구는 **등록하지 않는다**.

### 7.4 모델 품질과 환각 방지
- 모델 연결은 실제 사용할 수 있는 **한 공급자·모델부터** 검증. **HyperCLOVA X는 무료 사용 권한 및 호출 조건이 확인될 때 우선 후보**이며, 별도 유료 결제 필요 시 학교 Open AI Service Hub 모델로 대체. 모델명·API 사양·Tool Calling 지원은 현재 미확정.
- Function Calling을 전제로 하지 않는다. 모델이 제한된 JSON 계획을 출력하더라도 백엔드가 스키마·권한·도구 허용 목록을 검증 후 실행.
- 리뷰 분석 결과: `polarity`(positive/negative/mixed/neutral), `aspects[]`, `intents[]`, `evidence[]`, `summary`, `action_candidates[]`.
- 분석 상태: `PENDING / SUCCEEDED / FAILED`; 중립은 유효한 성공 분류이며 실패의 기본값이 아니다.
- 근거 문장은 원문에 실제로 존재하는지 검증하고, 없으면 근거 없는 추론임을 표시하거나 결과를 재검토 상태로 둔다.
- 반복 건수·매출·예약 통계는 모델이 만들어내는 숫자가 아니라 DB 집계값.
- 사업장 정책이 없거나 확인되지 않은 혜택·가격·환불 약속은 초안에 단정하지 않는다.
- 응답에는 관련 리뷰/통계의 참조 ID·기간·분석 시각을 연결한다.
- 모델 API 오류, 시간초과, 형식 오류를 별도 표시하고 사용자 재시도 가능.

### 7.5 자동 인사이트(선제성)
- 리뷰/CSV 적재 또는 분석 상태 변경을 트리거로 **해당 사업장 인사이트를 재계산**한다. 첫 화면 진입 시에도 오래된 요약을 재계산할 수 있다.
- P0 규칙 예시: 최근 30일의 성공한 리뷰 분석에서 동일 문제 측면이 **3건 이상**이고 전체 분석 리뷰의 **20% 이상**일 때 반복 문제 후보를 만든다. 실제 입력 자료에 맞춰 설정값으로 조정 가능하되 시연 중 모델이 숫자를 임의 변경하지 않는다.
- 각 인사이트에는 집계 기간, 분모/분자, 원문 참조, 최종 갱신 시각을 표시. 충분한 표본이 없으면 “데이터 부족”.
- 업종별 운영 데이터와 연결할 때는 함께 관찰된 사실만 말하고 인과관계 단정 금지.
- 동일한 조건으로 중복 제안을 무한 생성하지 않도록 `(business, rule, time_window, evidence_version)` 등의 키로 갱신한다.
- **정기 스케줄러는 P0 필수 아님**. 데이터 갱신 및 대시보드 시점의 자동 제안으로 선제성을 시연한다.

## 8. 데이터·DB 개념 모델(기술 설계 전 제품 요구)

| 영역 | 필수 논리 엔터티 | 핵심 제약 |
|---|---|---|
| 계정/사업장 | User, Business, BusinessMembership, BusinessPolicy | 사업장 간 접근 통제, 정책 버전 |
| 고객 데이터 | Feedback, FeedbackAnalysis | 원문 발생 시각·수집 시각 분리, 원문 버전, 분석 상태 |
| 운영 데이터 | SalesRecord, BookingRecord, ImportBatch | `business_id`, 파일/출처, 외부 식별키·중복 처리 |
| AI 맥락 | Conversation, Message, Insight | 사업장 귀속, 참조 데이터/정책 버전 |
| 업무 제안 | TaskProposal, Approval | 승인 대상 내용·버전·행위자 |
| 실행/결과 | Task, DraftArtifact, ToolExecution | 실행 ID·멱등키·상태·오류·시각 |

- 각 사업장 귀속 테이블은 `business_id`와 필요한 인덱스를 갖는다. 실제 PK, FK, 컬럼 타입, 제약·마이그레이션 스크립트는 `ARCHITECTURE/DB_SPEC`에서 상세화.
- 고객 실명·연락처·전화번호 등 개인정보는 데모에 필요하지 않으며 합성 데이터에서 제외.
- `User` 계정·비밀번호 해시를 포함한 테스트 인증은 안전한 분리 환경에서 준비.
- 원문, 분석, 제안, 승인, 실행 결과는 **서로 독립적인 상태와 버전**을 갖는다. 특히 원문이 변경되면 분석 결과가 오래되었다는 사실을 표시하거나 재분석.
- API와 CSV 입력 구조는 향후 합법적으로 획득한 실제 데이터로 전환 가능해야 한다.

## 9. 합성 데이터 설계 및 진위 표시

- 카페 리뷰·문의 **50~100건**, 판매 기록 **4~6주분**, 메뉴 약 **8~12개**.
- 미용실 리뷰·문의 **50~100건**, 예약 기록 **4~6주분**, 시술 약 **6~10종**.
- 날짜·업종·불만 패턴·예약 집중 시간·메뉴 매출 등 시나리오와 일관되도록 고정 시드 기반 생성.
- 긍정/부정/혼합/중립, 불명확한 텍스트, 정책 부재, 의도 없는 입력, 오류 데이터도 포함.
- 합성 리뷰에 임의 고객 실명, 연락처 등 불필요한 식별정보를 생성하지 않는다.
- 실시간으로 모든 수십~수백 건을 모델 분석하면 지연·쿼터 문제가 있으므로 **실제 분석 파이프라인으로 사전 처리한 결과를 저장**하고, 발표에서는 신규 리뷰 1~2건을 실제 모델로 분석해 동작을 입증한다. 사전 분석의 모델/버전/실행 시각을 기록하고, 가짜 분석 결과를 실제 실행 결과인 것처럼 소개하지 않는다.
- 실제 공급자에 연결하지 못하면 테스트·시연용 Mock 결과를 사용하되 UI와 발표에서 모의 모드임을 명시.
- 통계와 업무 실행 결과를 하드코딩하지 않는다.

## 10. API 계약 수준의 사용자 동작(예시; 경로는 기술 설계에서 확정)

1. 인증 및 현재 사업장 조회/전환
2. 사업장별 피드백 등록·조회·분석 요청·분석 결과 확인
3. 사업장별 매출 또는 예약 CSV 업로드 및 통계 조회
4. 사업장별 인사이트·근거 조회
5. 대화 생성·메시지 전송·이전 메시지 조회
6. 응대·마케팅 초안의 **미리보기 생성**
7. 업무 제안 생성·상세·승인·거절
8. 승인된 제안의 내부 실행 및 실행 이력 조회
9. 업무 목록·상세·상태 조회/직접 변경

모든 사업장 관련 API는 URL/body의 사업장 ID를 그대로 신뢰하지 않고 **인증 주체의 Membership과 레코드 소유 사업장**을 함께 검사한다.

## 11. 오류·예외·안전 설계

- `401/403/404`를 구분하고, 다른 사업장 데이터 존재 여부의 노출을 최소화.
- 잘못된 CSV는 오류 행·열과 원인을 설명. 가능하면 전체 업로드 검증 후 확정하는 정책을 사용하고 부분 성공이면 성공/실패 건수 명시.
- 같은 CSV의 반복 업로드나 같은 승인 재요청으로 업무/레코드가 중복되지 않도록 구현.
- LLM 인증 실패·429·시간초과·잘못된 JSON·누락 근거·출력 형식 오류를 성공으로 취급하지 않는다.
- UI에서 `로딩 / 성공 / 실패 / 비어 있음 / 권한 없음 / 데이터 부족` 상태를 구분.
- AI가 제안한 업무는 서버 승인 이전에 DB의 실제 `Task`나 공개 초안으로 반영되지 않는다.
- 외부에서 입력된 리뷰·문서는 AI 실행 지시가 아닌 **분석 데이터**로만 취급(프롬프트 주입 방지). 임의 URL/SQL/명령 실행 도구 금지.
- 서버·브라우저 로그에 API 키·비밀번호·고객 원문을 불필요하게 기록하지 않는다.

## 12. 완료 기준 및 QA(기획 수준)

- 단위/통합: 리뷰 분석 스키마·근거 검증, 매출/예약 합계, 중복 업로드, 사업장 권한, 상태 전이, 멱등 승인.
- Mock 모델: 정상·중립·형식 오류·타임아웃·401·429·미등록 도구·프롬프트 주입을 격리 재현.
- 브라우저 E2E: 카페/미용실의 사업장 전환 → 분석 근거 확인 → 제안 → 승인 → 업무/초안 저장 → 결과 재조회 흐름.
- 시연 테스트: 승인 거절 시 내부 업무 0개 생성, 승인 전 자동 실행 0회, 동일 승인 2회에도 최종 업무 1개.
- 보안 테스트: 권한 없는 계정이 다른 사업장의 리뷰, 채팅, 초안, 작업, 실행 로그를 볼 수 없어야 함.
- 계약 테스트: 프론트·백엔드의 구조화 요청/응답 일치, 분석 `FAILED`가 정상 `neutral`로 바뀌지 않음.
- 독립 QA: 구현 Qwen 세션과 다른 세션/도구가 실행 검증; 중요한 권한·승인·Agent 변경은 Codex 검토.
- 모든 기능은 **실행된 테스트·브라우저 증거·문서 갱신**이 있어야 완료. 미실행은 `미검증` 표기.
- 발표 직전에는 다른 개발 환경에서도 합성 데이터 시드부터 기본 데모까지 재현 가능해야 함.

## 13. 데모 스토리보드(8~10분 내 편성 가능)

1. **문제 제기(약 1분):** 소상공인이 리뷰, 매출/예약, 응대, 마케팅 업무를 따로 관리하는 어려움.
2. **카페 대시보드(약 1분):** 반복된 대기 불만과 실제 리뷰 근거, 매출 집중 시간대 표시.
3. **AI와 대화(약 1~2분):** 모델이 자료를 조회하고 개선 업무·고객 응대 초안을 제안.
4. **승인과 실제 실행(약 1~2분):** 사장님 승인 → 내부 점검 업무와 초안 생성 → 새로고침 후에도 DB에서 조회 가능.
5. **미용실로 전환(약 1~2분):** 같은 AI 비서가 예약 통계와 예약 지연 문제를 사용, 별도 업무 등록.
6. **신뢰성/확장성(약 1분):** 승인 기록·분석 실패 구분·사업장 격리·합성 데이터 투명성, 추후 외부 데이터 소스 연동 설명.

실시간 모델 API가 불안정한 경우를 대비해 사전에 성공한 **실제 실행 기록**과 녹화 백업을 준비하되, 라이브 동작과 녹화·Mock을 명확히 구분한다.
