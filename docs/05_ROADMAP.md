## 4. 작업 흐름 (하루 반복)
1. 오전/작업 시작 10분: 각자 작업 1개, 목표 AC, 영향 파일 공유.
2. 작업별 feature branch `feat/<story-id>-...`, base = `dev`. 최소 PR 단위는 0.5~1일 크기.
3. Qwen에는 SRS 요구사항 ID·API 계약·파일 허용 범위·테스트 기대값을 전달.
4. 구현 후 **로컬 테스트 출력 + Git diff** 확보. 성공하지 않은 실행은 실패로 남김.
5. Codex 읽기 전용 검증(고위험: auth/tenant/approval/provider/DB migration). 발견 사항을 Qwen에 **작은 수정**으로 반환.
6. 상대가 PR 검토: 수정 파일·권한 경계·회귀 테스트·UI 영상 확인 후 머지.
7. 머지 뒤 `dev` 통합 E2E 실행. `main`은 검증된 시연 후보 태그만 올림.

## 5. Git 충돌 줄이기
- A와 B는 `frontend/`/`backend/` 폴더 소유권 분리. API 명세는 단일 오너 없는 공유 계약 문서, 양측 승인 필요.
- migration 동시 작업 금지: A가 번호/순서 관리. B의 조회 API는 고정 모델을 기준으로 구현.
- 동일한 `AGENTS.md`, `PRD.md`, `API_CONTRACT.md`를 에이전트 세션별 로컬 문서로 불러오고 읽었는지 요약 확인.
- UI 디자인은 B 소유, 승인/보안 규칙은 A 소유. 양측 기능 영향 시 먼저 계약 변경 PR.
- 긴 시간 돌리는 에이전트는 별도 작업 트리/브랜치; 서로 동일 파일을 병렬로 고치지 않도록 체크.

## 6. 막혔을 때 축소/대체 규칙
- HCX 무료 키 부재 → 학교 허브 모델로 실행, UI 제공자 표기 정확히. 둘 다 미연결 → Mock은 테스트 전용, 실제 LLM 필수 주장 금지.
- 네이버 공식 리뷰 API 불가 → 합성/사용자 파일로 입력 대체, 지역성은 매장 위치·업종 맥락으로 제한.
- 모델 전체 100건 분석 지연 → 최초 1회 실제 분석된 결과 저장+신규 1~2건 라이브 검증(캐시 provenance 기록).
- 팀원 BE 경험 부족 → read-only 조회 API만 맡고 A가 schema/migration/권한 및 리뷰 담당.
- 마지막 10일에 결함 폭증 → 미완료 P0 중 핵심 외 기능은 제거/비활성, 보이지 않는 기능 구현 주장 금지.
